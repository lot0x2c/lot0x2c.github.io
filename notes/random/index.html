random vs secure

2026-11-23 · security, crypto

Most languages give you two ways to get a random number, and they look interchangeable. They aren't. One is fine for shuffling a playlist and dangerous for making a password; the other is fine for both. This is how to tell them apart, and why there are two.

Two meanings of "random"

In programming, "random" usually means pseudorandom: a deterministic sequence that looks random. A pseudorandom number generator (PRNG) keeps some internal state, and every call does two things: it computes an output from the state, and it updates the state. Start from the same state, which is set by a number called the seed, and you get the same sequence every time.

Secure random means cryptographically secure: output nobody can feasibly predict, even someone who knows the algorithm and has seen every output so far. A generator with that property is a CSPRNG.

The difference isn't how random the numbers look. A decent PRNG passes the usual statistical tests, and so does a CSPRNG. The difference is who can predict the next one.

How a plain PRNG gives itself away

The simplest PRNG is the linear congruential generator: multiply, add, take the remainder. This one uses the multiplier and increment from the example in the C standard. The standard's version throws away some of the bits before handing you the rest. I kept them all, because it makes the problem easier to see:

static unsigned long state = 1;

unsigned long next(void)
{
    state = (state * 1103515245 + 12345) % 2147483648;
    return state;
}

The output is the state. So if you see one output, you know the state, and you can compute every output after it by running the same line. A generator whose state you know is a list of numbers. You can just read ahead.

Better PRNGs hide their state better, but not well enough to matter here:

  • The Mersenne Twister, behind Python's random, Ruby's rand and PHP's mt_rand, can be rebuilt from 624 consecutive 32-bit outputs. After that, every prediction is exact. PHP returns 31 of the 32 bits, which makes it more work.
  • Math.random() in V8 (Chrome, Node) uses xorshift128+. People have recovered its state from a handful of outputs with an SMT solver, a program that finds values satisfying a set of equations. The exact number of outputs depends on the engine version.

None of these generators is broken. Being hard to predict was never their job.

Seeds can be guessed too

Even when the outputs stay hidden, the seed may not. A common pattern is seeding with the current time in seconds, as in srand(time(NULL)). If an attacker knows a token was made in the last hour, there are 3,600 possible seeds, and trying all of them takes a laptop a fraction of a second. The seed was a secret that every clock in the building was displaying.

What makes a generator secure

A CSPRNG needs two things: a seed nobody can guess, and a construction in which the outputs reveal nothing useful about the state.

The kernel handles the seed. It collects unpredictable events from the hardware, such as interrupt timings and, where the CPU has one, its hardware random number instruction, and mixes them into a pool. For the second part, Linux and OpenBSD both use the ChaCha20 stream cipher as the generator. Working out its state from its output would mean breaking ChaCha20.

You don't build one yourself. You ask the system:

predictable (games, simulations, tests) secure (tokens, keys, passwords)
C rand(), random() getrandom(2), arc4random(3)
Python random secrets, os.urandom
JavaScript Math.random() crypto.getRandomValues()
Go math/rand crypto/rand
shell $RANDOM /dev/urandom

OpenBSD is an exception to the left column. Since 5.7, rand() and random() there return secure output unless you call srand_deterministic(). It's the one system I know of where rand() is fine for passwords, and it got there by ignoring the seed you gave it. Go is a partial exception: recent versions start math/rand from a random seed, but its documentation still says it should not be used for security-sensitive work. I'd believe the documentation.

A concrete case: password reset tokens

This looks like a random token:

const token = Math.random().toString(36).slice(2);

Here's what goes wrong. An attacker asks for a few password resets for their own account and reads the tokens from their own email. Those are outputs of Math.random(). From them they rebuild the generator's state, ask for a reset for your account, and compute the token that was just emailed to you. They never see your email. (This assumes both requests hit the same server process, so the same generator. On a single small server, they usually do.)

The fix is about the same length:

const bytes = crypto.getRandomValues(new Uint8Array(32));
const token = Array.from(bytes, b => b.toString(16).padStart(2, "0")).join("");

That's 256 bits from the system's CSPRNG. In Python it's one call: secrets.token_urlsafe(32).

Looking random isn't being unpredictable

I said both kinds pass statistical tests. That deserves a closer look, because it's why this mistake is so easy to make. Standard tests, like the frequency and runs tests in NIST SP 800-22, compare a sample of bits with what fair, independent coin flips would produce. A test can only reject. A large p-value means the test found nothing; it doesn't mean there's nothing to find.

Each test also checks one thing. The frequency test counts ones. A source whose bits repeat the previous bit 90% of the time still has about half ones and half zeros, so in the long run its count looks right, while the last bit tells you the next one nine times in ten. The runs test catches that particular pattern, and some other pattern slips past both. A deterministic generator can pass every test you run on a finite sample while its whole future is already fixed by its state. The test asks how the numbers look, and they look great.

How much a weak key leaks

The project Does Random Mean Secure? by tdvnm measures this in the smallest setting where every number can be computed exactly. Messages and keys are two bits, and the cipher is C = M xor K, a one-time pad. The messages 00, 01, 10, 11 have probabilities 0.4, 0.3, 0.2 and 0.1. Each key bit is 1 with probability q: at q = 0.5 the key is fair, and above that it's biased.

Leakage is measured as mutual information: how many bits, on average, seeing the ciphertext tells you about the message. Zero is perfect secrecy. The message itself carries about 1.85 bits.

q key entropy (bits) leakage (bits)
0.50 2.000 0.000
0.60 1.942 0.052
0.70 1.763 0.214
0.80 1.444 0.503
0.90 0.938 0.966
0.95 0.573 1.304

A slightly biased key leaks a little; a badly biased one leaks most of the message. At q = 0.95 the key is 11 about 90% of the time, so if you see the ciphertext 11, the chance that the message was 00 goes from 0.40 to about 0.94. The message is still encrypted. It's encrypted with something you could have guessed.

Bias isn't the only way to fail. Take a key whose bits are each fair, but where the second bit copies the first 90% of the time. With the same messages, every ciphertext comes out exactly equally likely, so the ciphertext alone looks perfect, and it still leaks about 0.53 bits. The project's simulation covers this case too.

The project is careful about scope, and so is this: it's one cipher, one message distribution and one family of keys. It shows that in this setting a more predictable key leaks more. It doesn't say how much any particular real system leaks.

The objections

"/dev/random is more secure than /dev/urandom, because it blocks." That was the old advice. On Linux since 5.6, /dev/random blocks only until the pool has been seeded once at boot, and after that both files give output from the same CSPRNG. getrandom(2) with no flags behaves the same way. Use either.

"Secure random is slow." It's slower than xorshift, and it doesn't matter for tokens: you need 32 bytes, not a billion. The cases where a fast PRNG is worth it, like simulations that draw billions of numbers, are cases where you didn't need secrecy anyway.

"So always use the secure one?" Not always. A seeded PRNG is predictable on purpose. In a simulation, a test or a game's world generator, getting the same sequence from the same seed is the feature. It lets you replay exactly what happened, including the bug.

The rule

If anyone would gain something by predicting the number, use the secure generator. If you'd gain something by reproducing it, use a seeded PRNG and write the seed down. If neither, either works, and the secure one is the safer default.
