why nixos

2026-11-23 · nix, linux

I run NixOS on my laptop. This is about why, and what it costs, so you can decide whether the trade makes sense for you. The short version: NixOS keeps a written answer to the question "why is my computer like this?", and most systems don't.

What "declarative" means

People call NixOS "declarative", usually without saying what that means. It's the word that explains the rest, so I'll start there.

On most systems you get a working setup by doing things in order: install a package, edit a file, enable a service. The system is the sum of every command anyone ever ran on it. The record of those commands is your shell history, which has a size limit, and your memory, which doesn't tell you when it's full.

"Declarative" means you write down what the system should be, and a program works out how to get there. On NixOS that description lives in /etc/nixos/configuration.nix. You don't install fish. You write down that your shell is fish, and rebuild. Here's a trimmed piece of mine:

{ pkgs, ... }:
{
  imports = [
    ./modules/audio.nix
    ./modules/network.nix
    ./modules/power.nix
    # ...
  ];

  users.users.you = {
    isNormalUser = true;
    shell = pkgs.fish;
    extraGroups = [ "wheel" ];
  };
  security.sudo.execWheelOnly = true;

  # install-time version, never bump it
  system.stateVersion = "26.05";
}
How it works
  1. Every package is built into its own directory under /nix/store, named by a hash of everything that went into building it: the source, the dependencies, the build options. Change any input and you get a different hash, so a different directory. Nothing is built over the top of something else.
  2. The whole system, meaning the kernel, the services and the files in /etc, is built the same way, as one more store path that refers to all the others.
  3. nixos-rebuild switch builds that path, then points /run/current-system at it and starts or stops services to match.
  4. The previous system is still in the store. It stays in the boot menu as an older "generation", which is NixOS's word for a complete system you used to have.

Two things follow. A build that fails never touches the running system, because building and switching are separate steps. (A switch can still go wrong, for instance when a service won't start.) And going back is just pointing at the old path again: nixos-rebuild switch --rollback, or pick the older generation at boot.

What I get out of it
  • The config is the documentation. Mine is 31 lines that import ten modules: audio, network, power, packages and so on. When I want to know how something is set up, I read the module. The other method was remembering.
  • Removing a line removes the thing. On most distributions, uninstalling can leave config files, users and enabled services behind. On NixOS, what isn't in the config isn't in the system after the next rebuild. To be exact about the scope: that covers packages, services and /etc. The old files sit in the store until they're garbage-collected, and your home directory and the data under /var stay.
  • Breaking things is cheap. A bad update costs one reboot into the previous generation. That's the whole penalty, as long as the bad update didn't also rewrite your data.
  • It can be reproduced. With the same config and the same pinned nixpkgs revision (a flake with its lock file, or a pinned channel), another machine builds the same system. Without pinning, "the same config" means the same config built against whatever nixpkgs is today, which is a weaker claim.
The objections

"The learning curve is steep." It is. Nix is a small, lazy, functional language, its error messages are often unhelpful, and the documentation is spread across the manual, the wiki and the source. You can get a long way by copying options from search.nixos.org, which lists every option with its type and default. I won't claim that makes the curve gentle.

"Downloaded binaries don't run." By default they don't, and it follows from step 1. A program built for other distributions expects its loader, the piece that starts it, at /lib64/ld-linux-x86-64.so.2, and its libraries in places like /usr/lib. NixOS keeps the libraries in the store. At the loader's path it puts a stub, a program whose only job is to say that your program can't run. The stub runs fine.

The fixes are to package the program, to run it in an environment that imitates the usual layout, such as steam-run, or to enable programs.nix-ld, which puts a working loader at that path. I enabled it, because pip wheels and npm downloads come as prebuilt binaries.

"It uses a lot of disk." Every generation keeps its packages alive. sudo nix-collect-garbage -d deletes the old generations and whatever only they were using, and nix.gc.automatic does it on a schedule. Mine runs weekly and drops generations older than 30 days. Undo is free; storing the undo isn't.

"It's just configuration management, like Ansible." The difference is the point. Ansible runs steps against a system that already exists, and whatever the playbook doesn't mention, it leaves the way it found it. Over time the machine drifts away from the playbook. NixOS builds its part of the system from the description every time, so that part has nothing left over to drift.

So

If you want to know why your system is the way it is, NixOS gives you a file that says so. The price is learning Nix, and some extra work to run programs that weren't built for it. For the machine I use every day, I think that's a fair trade. If you don't need to know why, you don't need NixOS.

If you want to find out, try it in a virtual machine first. The rollback menu goes back to every system you had on NixOS, and the one you had before NixOS isn't on it.

The other route to the same place is a system small enough to read all of. I wrote about that in bare minimum to get openbsd running. Either way, you end up with a system you can explain.
