regex

2026-11-23

A regular expression, or regex, is a pattern that describes a set of strings. You give a regex engine a pattern and some text, and it tells you whether the text contains a string from that set, and where. grep, sed, your editor's search and nearly every language's string library use them.

"Regular" here doesn't mean ordinary. It comes from formal language theory, where a regular language is one that a machine with a fixed, finite memory can recognise. That sounds like trivia, but it explains both what regexes are good at and the one thing they can't do, which comes at the end.

The examples use grep -E (POSIX extended syntax), and most other flavours agree with all of it. To follow along, grep -o prints only the part that matched:

echo 'concatenate' | grep -oE 'cat'

Literals

Most characters match themselves. cat matches "cat", and also the "cat" inside "concatenate" and "bobcat". Unless you say otherwise, a regex looks for a match anywhere in the text, not for the whole text.

Any character

. matches any single character. c.t matches "cat", "cot", "c7t" and "c t". It also matches a literal period, so 3.14 matches "3.14" and "3x14". To mean a period and nothing else, escape it: 3\.14. The same goes for the other special characters: \*, \+, \?, \(, \[, \\.

Character classes

Square brackets match one character from a set.

  • gr[ae]y matches "gray" and "grey".
  • [0-9] is any digit; [a-zA-Z0-9_] is a letter, digit or underscore.
  • A ^ right after the bracket negates the set: [^0-9] is any character that isn't a digit.
  • POSIX has named classes: [[:digit:]], [[:space:]], [[:alpha:]].

Perl-style flavours (Perl, Python, JavaScript, grep -P) also have shorthands: \d for a digit, \w for a word character, \s for whitespace. POSIX grep -E doesn't promise \d, so use [0-9] there.

Repetition

A quantifier applies only to the item right before it. ab+ means "a" followed by one or more "b"s, not "abab".

Watch out for * on its own. a* matches zero or more "a"s. Every string has at least zero "a"s, so a* matches every string ever written, at position zero. That's why grep -E 'x*' prints every line of the file.

Anchors

^ matches the start of a line and $ the end. They match positions, not characters.

  • ^#: lines that start with "#".
  • ^$: empty lines.
  • ^[0-9]+$: lines that are only digits. Without the anchors, [0-9]+ also matches "abc123", because "123" is in there.

Anchors turn "contains" into "is". A validator without them accepts any input that contains something valid, which is a different promise.

Groups and alternation

Parentheses make a group, and a quantifier after a group applies to the whole group: (ab)+ matches "ab", "abab", "ababab". | means "or": cat|dog.

| binds loosest of all, which is a common trap. ^cat|dog$ means "^cat, or dog$". You almost always meant ^(cat|dog)$.

Groups also capture what they matched, and a replacement can refer to the captures by number:

echo 'root@localhost' | sed -E 's/([a-z]+)@([a-z]+)/\2: \1/'
# localhost: root

Putting it together

Here's a pattern for an IPv4 address, read left to right:

^([0-9]{1,3}\.){3}[0-9]{1,3}$

Start of line; then, three times, one to three digits followed by a literal period; then one to three digits; then end of line. It matches "192.168.1.23". It also matches "999.999.999.999", which isn't an address. The regex checks the shape, not the meaning.

You can make each part accept only 0 to 255:

(25[0-5]|2[0-4][0-9]|1[0-9]{2}|[1-9]?[0-9])

That's correct, and it's also where regexes start being hard to read. For meaning, it's usually clearer to match the shape with a regex and then check the numbers in code.

One more trap: quantifiers are greedy. They take as much as they can while the rest still matches. On <b>bold</b>, the pattern <.+> matches the whole string, not just <b>. Perl-style flavours have a lazy version, <.+?>, but <[^>]+> works in every flavour and says what you mean: a "<", some characters that aren't ">", then ">".

What regexes can't do

Back to "regular". A regex can be turned into a finite automaton: a fixed set of states, and rules for which state to move to on each character. If the text runs out while you're in an accepting state, it's a match.

The number of states is fixed when the pattern is written, so the machine can only remember a bounded amount about what it has seen. Checking that parentheses are balanced means remembering how many are open, and that number has no upper limit. So no regular expression matches exactly the balanced strings. The same argument rules out HTML, JSON and anything else that nests to any depth. A regex can handle nesting up to a fixed depth you choose, and no further.

Some engines add features that go past this. Backreferences like (a+)b\1 and PCRE's recursion can't be done by a finite automaton, so a pattern that uses them isn't regular any more. It's still called a regular expression.

The objection: "regexes are write-only"

That's fair for long ones, and the long ones are usually doing a job that doesn't fit. The answer is to keep each regex to work it's good at: checking the shape of a short string, finding lines, pulling out a field. Anchor it, prefer a class like [^>] to ., and when a pattern needs a comment longer than itself, use a parser.

There's also a cost that isn't about reading. Engines in Perl, Python, JavaScript and Java backtrack: they try one way to match, and when it fails they back up and try another. A pattern with nested quantifiers, like (a+)+$ run on a long row of "a"s followed by a "b", has exponentially many ways to split the "a"s, and the engine tries every one before it gives up. Each extra "a" doubles the time, so the input that hangs your server is shorter than this sentence. A backtracking regex is what took down Cloudflare's network for about half an hour in July 2019. Engines built on automata, such as RE2, Go's regexp and Rust's regex, guarantee time linear in the input, and they pay for it by not supporting backreferences.

Summary

A regex describes a set of strings by their shape. Literals, ., classes, quantifiers, anchors and groups cover nearly every regex you'll read. Use them for shape, use code for meaning, and use a parser for anything that nests.
