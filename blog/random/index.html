random vs secure

2026-11-23

Most languages give you two ways to get a random number, and they look interchangeable. They aren't. One is fine for shuffling a playlist and dangerous for making a password; the other is fine for both. This is how to tell them apart, and why the difference exists.

Two meanings of "random"

In programming, "random" usually means pseudorandom: a deterministic sequence that looks random. A pseudorandom number generator (PRNG) keeps some internal state, and every call does two things: it computes an output from the state, and it updates the state. Start from the same state, called the seed, and you get the same sequence every time.

Secure random means cryptographically secure: output nobody can predict, even someone who knows the algorithm and has seen every output so far. A generator with that property is a CSPRNG.

The difference isn't how random the numbers look. Both kinds pass statistical tests for randomness. The difference is who can predict the next one.

How a plain PRNG gives itself away

The simplest PRNG is the linear congruential generator: multiply, add, take the remainder. This one uses the constants from the example in the C standard:

static unsigned long state = 1;

unsigned long next(void)
{
    state = (state * 1103515245 + 12345) % 2147483648;
    return state;
}

The output is the state. So if you see one output, you know the state, and you can compute every output after it by running the same line. A generator whose state you know is a list of numbers. You can just read ahead.

Better PRNGs hide their state better, but not well enough to matter here:

  • The Mersenne Twister, behind Python's random, Ruby's rand and PHP's mt_rand, can be rebuilt from 624 consecutive 32-bit outputs. After that, every prediction is exact.
  • Math.random() in V8 (Chrome, Node) uses xorshift128+. People have recovered its state from a handful of outputs with an SMT solver; the exact number depends on the engine version.

None of these generators is broken. Being hard to predict was never their job.

Seeds can be guessed too

Even when the outputs stay hidden, the seed may not. A common pattern is seeding with the current time in seconds, as in srand(time(NULL)). If an attacker knows a token was made in the last hour, there are 3,600 possible seeds, and trying all of them takes a laptop a fraction of a second. Seeding with the clock means anyone with a clock can play along.

What makes a generator secure

A CSPRNG needs two things: a seed nobody can guess, and a construction in which the outputs reveal nothing useful about the state.

The kernel handles the seed. It collects unpredictable events from the hardware, such as interrupt timings and, where the CPU has one, its hardware random number instruction, and mixes them into a pool. For the second part, Linux and OpenBSD both use the ChaCha20 stream cipher as the generator. Working out its state from its output would mean breaking ChaCha20.

You don't build one yourself. You ask the system:

OpenBSD is the exception to the left column. Since 5.6, rand() and random() there return secure output unless you call srand_deterministic(). It's the one system where rand() is fine for passwords, and it got there by ignoring the seed you gave it.

A concrete case: password reset tokens

This looks like a random token:

const token = Math.random().toString(36).slice(2);

Here's what goes wrong. An attacker asks for a few password resets for their own account and reads the tokens from their own email. Those are outputs of Math.random(). From them they rebuild the generator's state, ask for a reset for your account, and compute the token that was just emailed to you. (This assumes both requests hit the same server process, so the same generator. On a single small server, they usually do.)

The fix is the same length:

const bytes = crypto.getRandomValues(new Uint8Array(32));
const token = Array.from(bytes, b => b.toString(16).padStart(2, "0")).join("");

That's 256 bits from the system's CSPRNG. In Python it's one call: secrets.token_urlsafe(32).

The objections

"/dev/random is more secure than /dev/urandom, because it blocks." That was the old advice. On Linux since 5.6, /dev/random blocks only until the pool has been seeded once at boot, and after that both files give output from the same CSPRNG. getrandom(2) with no flags behaves the same way. Use either.

"Secure random is slow." It's slower than xorshift, and it doesn't matter for tokens: you need 32 bytes, not a billion. The cases where a fast PRNG is worth it, like simulations that draw billions of numbers, are cases where you didn't need secrecy anyway.

"So always use the secure one?" Not always. A seeded PRNG is predictable on purpose. In a simulation, a test or a game's world generator, getting the same sequence from the same seed is the feature: it lets you replay exactly what happened, including the bug.

The rule

If anyone would gain something by predicting the number, use the secure generator. If you'd gain something by reproducing it, use a seeded PRNG and write the seed down. If neither, either works, and the secure one is the safer default.
