why nixos

2026-11-23

I run NixOS on my laptop. This is why, and what it costs, so you can decide whether the trade makes sense for you.

What "declarative" means

NixOS gets described as "declarative", and that word does most of the explaining, so it's worth pinning down first.

On most systems you reach a working setup by doing things in order: install a package, edit a file, enable a service. The system is the sum of every command anyone ever ran on it. The record of those commands is mostly your memory, plus your shell history until it fills up.

Declarative means you write down what the system should be, and a program works out how to get there. On NixOS that description lives in /etc/nixos/configuration.nix. You don't install fish; you write down that your shell is fish. Here's a trimmed piece of mine:

{ pkgs, ... }:
{
  imports = [
    ./modules/audio.nix
    ./modules/network.nix
    ./modules/power.nix
    # ...
  ];

  users.users.you = {
    isNormalUser = true;
    shell = pkgs.fish;
    extraGroups = [ "wheel" ];
  };
  security.sudo.execWheelOnly = true;

  # install-time version, never bump it
  system.stateVersion = "26.05";
}

How it works

  1. Every package is built into its own directory under /nix/store, named by a hash of everything that went into building it: the source, the dependencies, the build options. Change any input and you get a different hash, so a different directory. Nothing is built over the top of something else.
  2. The whole system, meaning the kernel, the services and the files in /etc, is built the same way, as one more store path that refers to all the others.
  3. nixos-rebuild switch builds that path, then points /run/current-system at it and starts or stops services to match.
  4. The previous system is still in the store. It stays in the boot menu as an older "generation".

Two things follow. A build that fails never touches the running system, because building and switching are separate steps. And going back is just pointing at the old path again: nixos-rebuild switch --rollback, or pick the older generation at boot.

What I get out of it

  • The config is the documentation. Mine is a 30-line file that imports a dozen modules: audio, boot, network, power, hardening and so on. When I want to know how something is set up, I read the module instead of trying to remember.
  • Removing a line removes the thing. On most distributions, uninstalling leaves config files, users and enabled services behind. On NixOS, anything that isn't in the config isn't in the system after the next rebuild. To be exact about the scope: that covers packages, services and /etc. Your home directory and the data under /var stay.
  • Breaking things is cheap. A bad update costs one reboot into the previous generation. Breaking the system becomes something you can undo, which makes it much less exciting.
  • It can be reproduced. With the same config and the same pinned nixpkgs revision (a flake with its lock file, or a pinned channel), another machine builds the same system. Without pinning, "the same config" means the same config built against whatever nixpkgs is today, which is a weaker claim.

The objections

"The learning curve is steep." True. Nix is a small, lazy, functional language, its error messages are often unhelpful, and the documentation is spread across the manual, the wiki and the source. You can get a long way by copying options from search.nixos.org, which lists every option with its type and default. But I won't claim the curve is gentle.

"Downloaded binaries don't run." Also true, and it follows from step 1. A program built for other distributions expects its loader at /lib64/ld-linux-x86-64.so.2 and its libraries in /usr/lib. NixOS doesn't have those paths. It keeps exactly two files where other programs expect them, /bin/sh and /usr/bin/env, so that scripts can start and then find out nothing else is there. The fixes are to package the program, to enable programs.nix-ld, or to run it in an FHS environment such as steam-run.

"It uses a lot of disk." Every generation keeps its packages alive. nix-collect-garbage -d deletes old generations, and nix.gc.automatic does it on a schedule. Undo is free; storing the undo isn't.

"It's just configuration management, like Ansible." The difference is the point. Ansible runs steps against a system that already exists; anything the playbook doesn't mention, it leaves the way it found it. Over time the machine drifts away from the playbook. NixOS builds the system from the description every time, so there's nothing left over to drift.

So

If you want to know why your system is the way it is, NixOS gives you a file that says so. The price is learning Nix and giving up on running random binaries without a wrapper. For the machine I use every day, I think that's a fair trade.

The other route to the same place is a system small enough to read all of; I wrote about that in bare minimum to get openbsd running. Either way, you end up with a system you can explain.
